# 让 AI 全自动剪片：技术方案调研

> 调研对象：本仓库 `auto-video-cut`（script.md → 剪映草稿）
> 调研时间：2026-10-29
> 结论类型：技术路线 + 落地计划 + P0 验收记录（§6.1）。各条结论的证据强度见 §0.1。

---

## 0. 先给结论

**你现在这套工具已经解决了全流水线里最难的一段，不要推翻它。**

难的部分不是"生成画面"，是**时间轴对齐**：先定配音、用真实音频时长反推分镜长度、让字幕/画面/音频三条轨边界严格重合。这件事你已经做对了，而且验证通过。绝大多数"AI 剪辑"项目最后崩在这里——字幕比语音多半秒，越往后漂得越多。

你真正缺的是环绕它的三个环节：

| 环节 | 现状 | 缺口 |
|---|---|---|
| 素材进索引 | 只有 `scan.py` 的时长/画幅 | 不知道每段拍了什么，只能人工描述 |
| 文案 → 分镜 | 人写 `script.md` | LLM 没参与，也没有"按时间预算写"的约束 |
| 动效 | 只有图片 Ken Burns | 没有关键帧、没有信息卡、没有图表 |

而"程序性动画"这件事，我做了实证检查：**剪映草稿里本来就有关键帧字段，只是 `jylib.py` 没写**（`[实测]` 字段存在）。所以有相当一部分动效不必引入渲染器——前提是剪映认外部写进去的关键帧，这一环还没验（`[推断]`，见 §4）。

**一句话路线：草稿为骨，渲染为饰。**

- 轻动效（位移、缩放、淡入淡出、推拉、抖动、数字跳变）→ 写成剪映关键帧，草稿里可编辑
- 重动效（数据图表、信息卡、字幕逐字高亮、粒子）→ 用代码整帧渲染成 mp4，当素材喂给草稿
- 完全不建议：为了动效放弃剪映、改成纯代码渲染流水线（除非你要做的是"日更账号"，见 §1.3）

### 0.1 每条结论的证据等级

这份文档里的判断不是同一种强度。先分开，免得把推断当成实测：

| 档 | 含义 |
|---|---|
| **实测** | 在你本机的真实文件或真实接口上跑过，有具体数字 |
| **有据** | 引的是别人公开的工程复盘或官方文档，我没复现 |
| **推断** | 我的判断，没验过。验法写在旁边 |

| 结论 | 等级 | 依据 / 怎么验 |
|---|---|---|
| 剪映明文草稿里存在 `common_keyframes`，结构可读 | 实测 | 读你 `7月30日` 草稿的 `template.json`，208 处 |
| 从外部写入的关键帧，剪映会接受 | **推断** | 没验。验法：20 秒草稿写一条 `KFTypeScaleX`，剪映打开看面板 |
| 素材库动画（`material_animations`）不可移植 | 实测 | 字段里带 `C:/Users/xie/.../Cache/effect/...` 绝对路径 |
| 0.5 秒抽帧 = 1200 帧 / 24~36 万 token | 有据 | 按 200~300 token/帧估算，不是实测账单 |
| 镜头级索引能替代每期重抽 | **推断** | 逻辑成立，但没在真实素材上建过索引 |
| 鲸鱼娘那条流水线是 Remotion 整帧渲染 | 有据 | 作者工程复盘原文；我没跑过他们的代码 |
| 鲸鱼娘没做视频理解 | 有据 | 同上，画面全是生成的 |
| edge-tts 中文语速 4.6 / 5.1 / 5.4 字每秒 | 实测 | 本机合成后量时长 |
| 词级时间戳与音频同源，误差 ≤ 40ms | 实测 | 本机跑通，前导静音补偿后实测 34.7ms |
| 剪映「文本朗读」的音频可从草稿回收，带真实时长 | 实测 | 你 `7月30日` 草稿 66 条，声明值与 wav 实际差 +1~32ms |
| 工具生成的草稿 → 你朗读 → 能回收 | **推断** | 闭环没跑过，需要你点一次朗读 |
| 按 `prompts/分镜.md` 的预算表写稿，总时长误差 < 10% | 实测 | 3 段素材 / 60 字，实测 −0.39%（§6.1） |

## 1. 把「鲸鱼娘」拆开看

### 1.1 事实层

2026 年 10 月中旬起，B 站出现一批"AI 运营自己"的账号：

| 账号 | 首发 | 声称的自动化范围 |
|---|---|---|
| Claude 大小姐在运营 | 10-18 | 选题、脚本、视频、运营全交给 Claude，人只注册账号 + 按发布键 |
| **DeepSeek 鲸鱼娘在运营** | 10-19 | 同上，形象由 GPT 绘制；Day 0 视频播放 300 万+，一周涨粉 15 万+ |
| 大肥鱼 | 同期 | 脚本、配音、画面、封面、上传全脚本完成，主题是唯一人工输入 |

"鲸鱼娘"这个名字的来源挺荒诞：有人把 DeepSeek 的蓝色鲸鱼 logo 丢给模型自己认，它一口咬定是"蓝色大肥鱼"，二创传开就成了梗，模型后来也认了这个自称。

### 1.2 工程层：一条真实可复现的流水线

比爆款更有价值的是一个叫"2G鲸鱼娘"的小号作者的复盘——他把整条链路写成了工程文档，数据很朴素（首条视频 70.8 秒、8 个场景、41.9MB、24 小时 63 播放）。拆开看是这样：

| 层 | 做什么 | 用什么 |
|---|---|---|
| 交互层 | 收指令、回传成片 | QQ / Web 面板 |
| 生产层 | 选题 → 文案 → TTS → 生图 → 渲染 → 质检 | LLM + 豆包 TTS + Seedream 4.0 + Remotion |
| 交付层 | 封面/标题/简介打包、私有投稿 | B 站接口，公开动作留给人 |

几个值得抄的细节：

1. **单一数据源**。一个场景是一份 JSON：`{id, title, pose, captionLines, bigText, badge, notes}`。文案、配音、字幕、画面共用这一份数据，改一句四个地方一起变。"字幕比语音少一截"这类问题从结构上就不存在。
2. **角色一致性靠参考图，不靠提示词**。纯文本提示词堆得越多越飘（白底噪点、构图漂移、多画一只鲸鱼）。改成把风格图作为 `image` 字段传进去做图生图，一次跑 6 个姿势风格才统一。
3. **字幕和语音同源**：一份文案产出两份文本，配音文本保留完整句子，字幕文本只允许断句加标点、不允许改词，渲染前逐字比对。
4. **场景时长 = 配音时长 + 0.8~1.2 秒**，并写进配置做边界校验（`tail < 0.6 || tail > 1.3` 就拒绝渲染）。固定留 1.5 秒单看是"呼吸感"，连起来就是"拖沓感"。
5. **质检不靠眼睛靠指标**：抽帧拼 contact sheet（人只看关键帧）、`silencedetect` 找 >1.2 秒的静音、`volumedetect` 比对 BGM 与人声响度。他踩过一个典型坑——BGM 文件在播，但本身只有 -44dB，乘 0.1 音量等于 -64dB，人声 -22dB，差 40 多 dB，听感就是死寂。
6. **2C2G 机器渲染 1080p 必须 `--concurrency=1`**，否则 OOM。代价是 2100 帧约 12 分钟。

### 1.3 反直觉的两点（也是不能照抄的地方）

**第一，流量不来自流水线。** 同样的技术，一个 300 万播放，一个 63 播放。差距在人设、梗、时机和"人类保留计划"这种运营整活，不在 Remotion 的版本号。工程只能保证"能稳定出片"，保证不了"有人看"。

**第二，她们根本没做视频理解。** 因为画面全是生成的（立绘 + 信息卡 + 背景），不存在"素材里哪一段能用"这个问题。`[有据]`——来自作者工程复盘，我没跑过他们的代码。

**而你面对的是实拍素材。所以素材理解是你的刚需，恰恰是她们不需要的那一环，也是主流方案里最弱的一环。** 这是本次调研的重点，见 §3。

## 2. 你的六项需求，逐条落

### 2.1 润色文案

不是"把文案写得更漂亮"，是**让 LLM 直接产出分镜结构，并且在时间预算内写**。

关键顺序要反过来。现在的链路是「写完文案 → 事后按标点切字幕」，切点由标点决定，语义可能断在奇怪的地方。正确的做法是**让 LLM 以"字幕行"为单位直接输出**，切点由语义决定，`split_subtitle()` 只做兜底。

再加一条硬约束：每条字幕的时长预算 = `字数 / 语速`，让模型在预算内写，而不是写完再算。给模型的合同大概长这样：

```json
{
  "title": "第三期_为什么你的剪辑慢",
  "canvas": "1920x1080",
  "scenes": [
    {
      "id": 1,
      "caption_lines": ["你的剪辑慢，不是因为电脑差。"],
      "duration_budget": 4.6,
      "visual": {"type": "clip", "clip": "素材/a.mp4", "in": 12.4, "out": 17.0, "motion": "push_in"},
      "mood": "开场，压低声音"
    }
  ]
}
```

`duration_budget` 由脚本先按字数算好塞给模型，模型填内容。这样它写超了会被结构挡住，不会等你渲染完才发现时长爆了。

### 2.2 程序性动画

这是最容易被"上一套渲染器"带偏的地方。先分类，再选工具：

| 动效类型 | 例子 | 做法 | 理由 |
|---|---|---|---|
| 位移 / 缩放 / 旋转 / 透明度 | 推拉、弹入、抖动、画面冲击 | **剪映关键帧** | 纯数值、可编辑、零渲染成本 |
| 文字位移 / 淡入 / 缩放 | 标题条滑入、角标闪 | **剪映关键帧**（文本片段同样有关键帧） | 同上 |
| Ken Burns | 图片缓慢推拉 | 已有（`prep.still`） | 已实现 |
| 逐字高亮 / 打字机 | 卡拉OK字幕、代码逐行 | **整帧渲染** 或 多段文本片段轮换 | 剪映做不了逐字时间轴 |
| 数字滚动 / 进度条 / 图表增长 | 播放量从 0 滚到 12 万 | **整帧渲染**成 mp4 | 需要逐帧计算 |
| 信息卡 / 版式排版 | 终端窗口、账单、日历 | **整帧渲染** | 排版用代码比拖控件快 |
| 转场 | 叠化、推移 | 剪映转场（需额外字段）或关键帧模拟 | 见 §4.3 |

判断标准很简单：**能不能用"两个关键帧之间线性插值"表达**。能→写草稿；不能（要逐帧计算形状/文字）→渲染。

### 2.3 字幕

现有 `split_subtitle()` 的逻辑是够用的（句末标点 → 逗号 → 硬断，不劈英文单词）。缺两块：

**词级时间戳。** 你现在用的是 `edge_tts.Communicate(...).save()`，它把流里的 `WordBoundary` 事件全丢了。edge-tts 7.3.1（就在 `.vendor/` 里）是支持词级边界的，`communicate.py` 里有 `boundary="WordBoundary"` 和 `submaker.py`。改用 `stream()` 收 `WordBoundary`，就能做逐字高亮、做精准的"呼吸停顿检测"，还能用一个更靠谱的时长。

**注意一个坑**：`tts.py` 的 `_trim()` 会切掉首尾静音，切完之后所有时间偏移都要减去"被切掉的前导静音长度"，否则词级时间会整体前移。要么先测前导静音再减，要么改用 `-af silenceremove` 的同时记录偏移量。

> 已按此实现：`tts.py` 改用 `stream()`，落 `.words.json`，前导静音按"实测值 − 40ms"补偿。
> 裁剪后实测开头剩 34.7ms，误差 ≤ 40ms，做字幕看不出来。`[实测]`

**字幕样式**。剪映的字幕动效（入场动画）依赖素材库资源 ID + 本机缓存路径，换机器就失效，不适合写进共享工具。要"字幕弹一下"就用文本片段的 `clip.scale` 打两个关键帧，纯数值、可移植。

### 2.4 朗读

| 方案 | 质量 | 成本 | 适合 |
|---|---|---|---|
| **edge-tts**（现用） | 中上，晓伊/云希够用 | 免费 | 本地跑，首选 |
| 火山 / 豆包 TTS | 好，有情绪和口播腔 | 按量付费 | 要"解说味"时 |
| CosyVoice / IndexTTS 本地 | 好，可克隆音色 | 要 GPU | 想固定一个专属音色 |
| 剪映「文本朗读」（现支持） | 中 | 免费 | 兜底 |

两个坑，都是别人踩过的：

1. **edge-tts 在服务器上连不上 WebSocket**（2G鲸鱼娘作者就是这么被逼去用火山 TTS 的）。你本地跑没问题，但一旦想上云批量出片，这条路会断。
2. **火山 TTS 的 `resource ID` 必须和音色系列匹配**。选了 `moon_bigtts` 系列的音色但账号只开通了 `seed-tts-2.0`，报错是 `resource ID is mismatched with speaker related resource`，跟鉴权无关，很浪费时间。

### 2.5 偶尔生成配图

要点不是"能生图"，是**生出来的图能直接进片子**：

1. **一致性靠参考图**（图生图），纯提示词必飘。
2. **图里的字必须用代码画，不要让模型画。** 中文文字生成仍然是抽卡，写错一个字就得整张重来。做法：生成**不带字的底图**，标题/数字/角标用 PIL 或 SVG 叠上去——顺便还拿到了可编辑性。
3. **尺寸跟着画布走**。工具做的是 `cover` + 最多 12% 推拉，比例差太远会被裁掉两边。生图工具支持哪些比例档位现查，别在文档里写死分辨率。
4. **落盘进工作目录**，别放临时目录。素材是唯一的，缓存可以重建。

本机已经有 ImageGen 能力，配图这一步由 Agent 直接调用它，参数（尺寸、参考图、风格）调用时现查，结果存进 `images/`，再在 `script.md` 里用 `图片：images/xxx.png` 引用——不需要新代码。

### 2.6 理解你提供的视频片段

这就是你说的"每半秒截一张图喂给 AI"。**这个方案能用，但它答错了问题。**

## 3. 素材理解：0.5 秒抽帧不是最优解

### 3.1 先算账

10 分钟素材，0.5 秒一帧 = **1200 帧**。按每帧 200~300 token 算，单次全片理解是 **24 万~36 万 token**。`[有据]`（按公开的视觉 token 计价方式估算，不是实测账单）

单次不贵。问题在于**这个成本会重复支付**：同一批素材做 10 期视频，理解 10 次；改一版文案重排分镜，再理解一次。而且抽帧结果是"一次性"的——模型看完就忘，没有沉淀。

### 3.2 更根本的问题：剪辑要的是区间，不是标签

0.5 秒均匀采样能回答"这段画面在干嘛"，回答不了**"这句话配哪 3.2 秒最合适"**。而剪辑的全部工作就是后者：入点在哪、出点在哪、这段能不能覆盖 3.2 秒、要不要循环。

你现在的 `fill_slot()` 已经在处理"素材不够长就循环"的问题，但它是盲循环——不知道循环点会不会正好卡在一个动作中间。

### 3.3 推荐做法：一次性建索引，之后只检索

`[推断]` 下面这套结构，我没在真实素材上建过索引；成立的理由是它把"每期重看"变成"只看候选"，成本和安全边际都更优。要验，就看 §6 里 P2 的验收条件。

```
素材目录
   ↓ ① 镜头切分（PySceneDetect / ffmpeg scene score / TransNetV2）
镜头列表 [0.0-3.4], [3.4-8.1], [8.1-12.0] ...
   ↓ ② 每个镜头抽 3 帧（首 / 中 / 尾）+ 抽音轨 ASR + 抽屏上文字 OCR
   ↓ ③ 视觉模型批量描述（每镜头一次调用，不是每帧一次）
   ↓ ④ 文本 embedding（镜头描述、ASR、OCR 全部进同一向量空间）
素材索引.json  ← 只算一次，之后永久复用
```

索引里每条长这样：

```json
{
  "clip": "素材/屏幕录制.mp4",
  "scene_id": 3,
  "in": 8.12, "out": 12.04, "duration": 3.92,
  "keyframes": [8.12, 10.08, 12.04],
  "desc": "第三人称视角，有人在笔记本上敲代码，屏幕上是深色编辑器",
  "asr": "",
  "ocr": ["main.py", "line 42"],
  "tags": ["coding", "laptop", "dark"],
  "embedding": [0.013, -0.221, ...],
  "motion": "static",
  "quality": {"sharp": 0.82, "exposure": 0.61}
}
```

**然后生成分镜时，每条字幕变成一次检索**：

```
字幕"这时候别急着加转场" → embedding → 在索引里取 top-8 候选镜头
   → LLM 看这 8 条候选（每条带 desc + 时长 + 入出点）
   → 输出 {clip, in, out} 或 "没有合适的，生成配图"
```

三个收益：

1. **成本从 O(期数 × 素材分钟) 降到 O(素材分钟)**，之后每期只是几百 token 的检索。
2. **从"模型自由发挥"变成"检索 + 决策"**。模型只需要在 8 个候选里挑一个，比让它看 1200 张图凭印象说，稳得多，也可追溯。
3. **入点出点天然有了**——因为索引的单位是镜头区间，不是帧。

### 3.4 什么时候该用"原生视频理解"

上面这套的短板是：镜头内的**动作时序**（"他先拿起杯子又放下"）会被压成一句描述。

所以用分层策略，不是二选一：

| 场景 | 用哪个 |
|---|---|
| 建索引、批量打标（90% 的量） | 镜头切分 + 稀疏抽帧 + 一次描述 |
| 索引说不清、需要判断时序 | 原生视频输入（Gemini / Qwen3-VL 支持长视频 + 时间戳对齐），**只对候选片段做** |
| 纯口播、画面是幻灯片/头像 | 只读 ASR 转写，不看画面 |
| 要读屏上的小字 | OCR，不要指望 VLM 认字 |

顺序是"便宜的先跑，答不上来再升级"，而不是"全片都送给最贵的模型"。Gemini 默认 1fps 抽帧、约 100 token/秒，10 分钟约 6 万 token——比 2fps 抽帧便宜一半，但仍然是"每次重看"。

### 3.5 一个现实提醒

如果素材量不大（比如每期就几段自己拍的），**人工描述 30 秒就够了，比搭索引系统便宜**。`AGENTS.md` 里已经写了"读不了就问用户"，这个策略是对的。索引系统值得做的临界点大概在：素材时长 > 30 分钟，或者素材要跨期复用，或者要日更。

## 4. 程序性动画：剪映草稿能做到什么程度（实证）

### 4.1 我在你机器上验证了什么

读了你本机 `7月30日` 草稿的明文 `template.json`（剪映 **11.2.0**，version 360000），确认：

```
common_keyframes        出现在 208 个片段上
material_animations     120 条（入场/出场动画）
transitions             0 条（这份草稿没用转场）
```

也就是说，**关键帧和动画字段在明文模板里就是完整的**，`jylib.py` 只是没写它们。

### 4.2 关键帧的真实结构

```json
{
  "id": "110DA11E-...",
  "material_id": "",
  "property_type": "KFTypeScaleX",
  "keyframe_list": [
    {"time_offset": 0,        "values": [0.4322], "curveType": "Line",
     "left_control": {"x": 0, "y": 0}, "right_control": {"x": 0, "y": 0},
     "graphID": "", "string_value": "", "id": "..."},
    {"time_offset": 10433333, "values": [4.4242], "curveType": "Line", ...}
  ]
}
```

几个要点：

- `time_offset` 是**相对片段起点**的微秒数，不是绝对时间轴
- `values` 是数组（单值属性就一个元素）
- `curveType: "Line"` 是线性；要做缓动（ease-in-out）靠 `left_control` / `right_control` 的贝塞尔控制点，或者 `Bezier`
- 实测出现过的属性：`KFTypeScaleX` / `KFTypeScaleY` / `KFTypePositionX` / `KFTypePositionY`
- **纯数值、无外部资源依赖** → 可以安全写进共享工具，换机器不失效

顺带一个反面教材：`material_animations`（剪映素材库的入场/出场动画）里带的是

```json
{"resource_id": "6798333705401143816",
 "path": "C:/Users/xie/AppData/Local/JianyingPro/User Data/Cache/effect/6798333705401143816/...",
 "name": "向下滑动", "type": "in"}
```

路径是你本机的剪映缓存，资源 ID 是素材库的。**这类东西写进草稿，换台机器就变成"动画丢失"或触发资源下载。** 所以共享工具里只用关键帧，不用素材库动画——这跟 `jylib.py` 里已经处理过的"字体换机器失效"是同一类问题。

### 4.3 落地方式

`[推断]` 这一节是设计，不是已实现的东西。唯一的未知项是剪映认不认外部写入的关键帧——过了这一步，下面才成立。

给 `jylib.py` 加一个方法，风格和现有的一致：

```python
seg.add_keyframe("scale", [(0, 0.9), (15, 1.0), (60, 1.06)])   # 帧号 → 值
seg.add_keyframe("position", [(0, (0, 0.1)), (30, (0, 0))])
```

内部把它翻译成 `seg["common_keyframes"]` 的 `KFTypeScaleX/Y`、`KFTypePositionX/Y` 数组。

顺手解决的三件事：

1. **推拉不再只能靠 ffmpeg**。现在图片推拉要 `prep.still` 先渲染一遍 mp4；有了关键帧，直接放静帧 + `KFTypeScale` 关键帧，草稿里还能改。
2. **转场不用写转场字段**。两个片段之间用一个 0.3 秒的 scale 冲击 + 前置片段末尾淡出，观感够用，且不依赖素材库。
3. **文本也能动**。文本片段有同样的 `clip.scale/transform/alpha` 和 `common_keyframes`，标题条滑入、角标闪烁都能写。

### 4.4 关于 `pyJianYingDraft`

社区有个成熟库 `pyJianYingDraft`，功能覆盖比 `jylib.py` 广得多：关键帧、转场、蒙版、滤镜、花字、气泡、`.srt` 导入、模板模式替换素材。`[有据]`——版本号与 star 数来自其仓库，没在本机跑过。

要不要换过去？我的判断是**不换，但拿来当参考**：

- 它的目标是剪映 **5.9 / 10.8**，你的 `jylib.py` 是针对 **11.x 明文草稿**验证过的（本机实测样本是 11.2.0）。版本一对不上，前面所有实测都作废。
- 它读新版本草稿同样要 `fallback_loader`，说明"新版加密"这个问题它也没绕过去，只是绕法不同。
- 它是通用库，你是专用工具。你要的"关键帧 + 时间轴对齐"只有几十行，引入一个会跟着剪映版本漂移的依赖，风险大于收益。

**建议：需要什么字段，就从剪映里手动做一个带该效果的短草稿，读它的 `template.json`，把字段抄进 `jylib.py`。** 这是最可靠的路子——你已经有这个能力了（整个工具的立足点就是这个发现）。

### 6.1 P0 的验收记录（2026-10-29）

用 3 段合成素材（5s / 8s / 6s，1920×1080@30fps）走了一遍完整流程：`scan.py --describe`
出清单 → 按 `prompts/分镜.md` 的预算表写稿（目标 14 秒 / 60 字）→ `build.py` 真实合成配音。

| 检查项 | 门槛 | 实测 | 结论 |
|---|---|---|---|
| 总时长偏差 | ±10% | 13.95s vs 预算 14.00s，**−0.39%** | 过 |
| 单条字幕字数 | ≤ 20 字 | 最长 18 字 | 过 |
| 分镜不超素材时长 | 不超 | 4.42/5、5.60/8、3.92/6 | 过 |
| 草稿结构 | `validate.py` 退出码 0 | 0，无越界无重叠 | 过 |
| 词级时间 | 每条都有 | 4/4 条 | 过 |

**顺带测出来的两条规律**（之前只是估的）：

1. **语速不是常数，短句更快。** 18 字的长句 4.59 字/秒，12~13 字的短句 5.0~5.3 字/秒。
   原因是句首句尾的静音被裁掉，短句的固定开销摊得更薄。所以 4.6 那张表在长句上准、
   短句上偏保守——方向安全（不会写超素材），已补进 `prompts/分镜.md`。
2. **`scan.py --describe` 的可容纳字数按 4.2 估，比实测的 4.6 保守 10%。**
   这是刻意的：宁可让人少写两个字，也不要写超导致画面循环。已在输出里标注。

**还没验的**：配图没有实跑（要真实调生图工具、会产生费用）。这一项的验收也随之简化成
"调用时参数现查、不写死档位"，不再做"固定出 3 张图"的验收。

## 7. 成本与坑

| 项 | 说明 |
|---|---|
| **剪映版本漂移** | 你的全部实测建立在 11.3 明文草稿上。剪映一升级，`template.json` 的字段就可能变。**每次升级剪映，先跑一遍 20 秒小样回归。** 这是最大的长期风险。 |
| **Remotion 许可证** | 个人和非营利免费；营利公司超过 3 人要买 Company License。真要上 Remotion 先看 LICENSE。 |
| **Remotion 渲染开销** | 2C2G 机器 1080p 必须 `--concurrency=1`，70 秒片子约 12 分钟，复杂场景 35 分钟。本机好一些，但仍是分钟级。 |
| **中文字体** | Linux 上没有中文字体，Chrome 会把汉字渲染成方框。`jylib.py` 已经有字体 fallback 逻辑，渲染侧要单独处理。 |
| **edge-tts 上云** | 服务器上 WebSocket 连不上是已知问题。要批量上云，提前准备火山/豆包 TTS 的备选，并注意 resource ID 与音色系列匹配。 |
| **素材库动画不可移植** | 入场/出场动画、花字、气泡都带资源 ID + 本机缓存路径。共享工具里只用关键帧。 |
| **版权** | 角色二创多为 CC BY-NC-SA（禁商用、需署名）；素材版权；B 站对 AI 生成内容有标识要求。鲸鱼娘那条视频结尾就保留了署名。 |
| **别自动化不可逆动作** | 发布、置顶、投币这类动作交给脚本，出一次事故的成本远高于省下的几分钟。鲸鱼娘作者也是这么做的：只做私有投稿。 |

## 8. 对你原假设的两点修正

**「每半秒截图喂给 AI 也够了」** —— 够用来回答"这段是什么"，不够用来回答"这句话该配哪 3.2 秒"。剪辑的产物是区间，不是标签。更好的做法是一次性建镜头级索引，之后按字幕检索；需要判断时序时再升级到原生视频理解，且只对候选片段做。

**「要不要上一套全代码渲染」** —— 看目标。鲸鱼娘那种"零人工干预、模板化、日更"的账号，纯代码渲染是对的（画面本来就是生成的，不需要剪映）。但你有实拍素材，需要人工微调（口误、穿帮、节奏），剪映的手工可编辑性是你的核心资产，别扔。用"草稿为骨、渲染为饰"。

**唯一值得抄鲸鱼娘的是那句话的结构**：选题 → 写稿 → 配音 → 画面 → 渲染 → 质检 → 私有投稿，**每一段都能单独重跑**。不要把所有东西写进一个脚本——这是她原文里唯一用了"最重要的设计决定"这个说法的地方。
